# Supabase integration

Module: `hermes_cli.integrations.supabase`
Skill:  [`skills/supabase-architect/SKILL.md`](../../skills/supabase-architect/SKILL.md)
Policy: [`docs/integrations/integration-policy.md`](./integration-policy.md)

## What it does

Helps the agent design a Supabase schema and emit a migration file the
operator can review, version-control, and apply with the `supabase`
CLI.

The adapter is deliberately the **local** path. The Supabase MCP server
operates on a project that's configured server-side and can issue
`apply_migration` directly to that project — useful but heavyweight.
This adapter produces a SQL file under
`supabase/migrations/<timestamp>_<slug>.sql` instead, so the change
goes through the same code-review process as any other repo change.

## What it never does

- Run `supabase db push` against a remote project.
- Hit the Supabase REST API.
- Commit secrets. Service-role keys and JWT secrets live in
  `~/.hermes/.env` or the operator's shell, never in a migration.
- Apply a migration in-place that has already been pushed. Schema
  changes after a push go in a *new* follow-up migration.

## CLI requirements

| Tool       | Required? | Used for                          |
|------------|-----------|-----------------------------------|
| `supabase` | yes for execute | local stack + migration apply |

`detect()` also reports whether a `supabase/` directory exists at the
project root (i.e. whether `supabase init` has been run).

## Designing a schema

```python
from hermes_cli.integrations import supabase as sb

users = sb.TableSpec(
    name="users",
    columns=[
        sb.ColumnSpec("id", "uuid", primary_key=True, default="gen_random_uuid()"),
        sb.ColumnSpec("email", "text", nullable=False, unique=True),
        sb.ColumnSpec("created_at", "timestamptz", nullable=False, default="now()"),
    ],
    comment="Application users.",
)

plan = sb.plan(migration_name="add users table", tables=[users])
print(sb.explain(plan))
sb.execute(plan, approve=True)   # writes the migration file
```

The generated migration always:

- Uses `create table if not exists` (idempotent).
- Enables row-level security (`alter table … enable row level security;`)
  unless `enable_rls=False` is set explicitly.
- Carries a `-- Generated by hermes_cli.integrations.supabase` header.

## Local-first command sequence

`plan().local_commands` returns:

```bash
supabase start
supabase db reset
supabase db diff --use-migra
```

Run those locally to confirm the migration applies cleanly on an
empty DB and produces no drift.

## Remote command sequence (approval gated)

`plan().remote_commands` returns:

```bash
supabase link --project-ref <project-ref>
supabase db push
```

The adapter prints these but never runs them. The operator runs them
themselves, in a shell that has the appropriate access token loaded.

## Migrations folder policy

- All migrations live under `supabase/migrations/`.
- Filename format: `YYYYMMDDHHMMSS_<slug>.sql` (UTC timestamp).
- Migrations are append-only after they've been pushed remotely. To
  change something already in production, write a new follow-up
  migration.
- Seed data with PII goes in a `.gitignored` seed file, not the
  migration.

## Secrets policy

- The migration SQL may reference *roles* (`grant select on … to anon`)
  but never embeds JWT secrets, API keys, or passwords.
- `~/.hermes/.env` holds `SUPABASE_*` keys for the local stack;
  production keys live in the operator's shell or password manager.
- The adapter does not read, store, or transmit any Supabase
  credential.

## Rollback

- Delete the freshly written migration file and re-run
  `supabase db reset` to drop the change locally.
- For a remote rollback, write a follow-up migration that issues the
  inverse DDL. Never edit a migration that has already been pushed.
- If `supabase db push` failed mid-way, capture the error, then re-link
  and retry only after the underlying issue is fixed.

## Validation

- `supabase db reset` succeeds.
- Project tests pass against the local stack.
- `supabase db diff` reports no drift.
- Every new table has either an RLS policy or a documented bypass.
